Audit chain

Every runtime and administration event of a tenant is hash-chained into an append-only record. This screen recomputes the whole chain and reports a computational fact — together with what that fact cannot mean.

Full recomputation on demand — O(n) in time and memory; a long chain takes longer. Nothing is cached client-side. A wrong id and one outside your key's scope both answer 404.

What this verifies

Full recomputation: every entry's hash is rebuilt from its stored fields and checked against the recorded value and its link to the previous entry.

Detects
  • Any altered entry content
  • Any broken link between entries
  • Missing or out-of-order entries
  • Malformed entries
Does not detect

A wholesale rewrite by an actor holding database-owner privileges, recomputing every hash from the point of change onward and rewriting the chain head. Recomputation alone cannot tell that apart from an honest chain.

Telling them apart needs a per-entry signature with a key the database never holds. The slot exists in the schema; the capability does not yet. When it lands, this panel's text changes — the layout does not.

Scope text comes verbatim from the API. It is part of the verdict, not a footnote.

Running · O(n), so say so

Button disabled with "Recomputing…", figures as skeletons. No fake progress bar: the API returns one answer at the end, so a percentage would be invented. On a long chain the wait is the honest signal that work is happening.
