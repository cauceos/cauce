Invocations — the states that matterSpec

Six rows above, all from real behaviour already seen in this project: two clean completions, one provider failure on the typo'd model, one that sat 3:24 and completed alone when Ollama came back, one still in flight, and one the client stopped watching at the 5:00 cap. That last one is UNKNOWN, not failed — the difference is the whole point of this screen.

UNKNOWN ≠ FAILED
UNKNOWNFAILED

Dashed border for UNKNOWN: the client stopped watching, the invocation kept living. FAILED means the server said so. Conflating them would be the easiest lie on this screen — the dashes exist to prevent it.

Recovered · the 3:24 row

A provider outage shows as a long slate bar with a thin teal tip. No resend, no duplicate — the queue held it and the reply arrived on poll 98. The shape tells the story before any text does.

Reaper-abandoned · named gap
Not shown, because it can't be. An invocation abandoned by the reaper leaves no conversation-visible trace and no client-visible terminal status. It would appear here as UNKNOWN forever. Naming it is the honest move until a failure signal exists server-side.

Absent on purpose
No tokens. No cost. No per-phase server timings. LlmUsage is logged but never persisted or attributed per tenant, and the API exposes no queue/model/tool split. Columns for them would be invention.

When usage persistence lands, this is the screen that gains a column — and the first place the commercial model becomes visible.
